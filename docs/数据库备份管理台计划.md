# 自部署数据库备份管理台计划

## 1. 背景与目标

当前需求是为用户提供一个可自行部署的数据库备份工具，用于把一台服务器上的数据库定期备份到另一台服务器上。

第一版目标不是做内部脚本，而是做成面向用户的 Web 管理台，让用户可以通过界面完成数据库连接配置、备份目标配置、定时任务配置、运行状态查看和失败日志排查。

## 2. 产品定位

- 产品形态：Web 管理台。
- 部署模式：用户自部署。
- 交付方式：Docker Compose。
- 第一版范围：备份配置、定时执行、备份记录、运行日志、失败监控。
- 第一版暂不做：一键恢复、跨云对象存储、增量备份、主从复制管理。

## 3. 第一版能力范围

### 3.1 支持的数据库

第一版支持：

- MySQL
- PostgreSQL

后续可扩展：

- SQL Server
- 达梦数据库
- Oracle
- MariaDB
- KingbaseES
- OceanBase
- 其他支持命令行导出或备份工具的数据库

### 3.2 支持的备份目标

第一版支持通过 SSH 上传到另一台服务器：

- 使用 `rsync` 或 `scp` 传输备份文件。
- 优先支持 SSH key 认证。
- 支持配置目标服务器地址、端口、用户名和目标目录。

后续可扩展：

- S3 兼容对象存储
- 阿里云 OSS
- 腾讯云 COS
- MinIO
- FTP/SFTP
- 本地 NAS 挂载目录

### 3.3 备份频率

第一版默认支持每日全量备份。

建议保留 cron 表达式能力，方便后续扩展为每小时、每周或自定义周期。

## 4. 推荐技术架构

### 4.1 总体架构

推荐采用单体应用架构：

- 一个后端服务同时负责 API、Web 静态资源、任务调度和备份执行。
- 使用 SQLite 保存系统配置和运行记录。
- 使用 Docker Compose 交付，降低用户部署成本。

这种方式适合第一版产品，部署简单、依赖少、用户容易理解。

### 4.2 服务组成

Docker Compose 中建议包含：

- `backup-manager`：主应用服务，提供 Web UI、API、调度器和备份执行器。
- `data` volume：保存 SQLite、密钥、任务配置和运行记录。
- `backups` volume：保存本地临时备份文件。

主应用容器内建议预装：

- `mysqldump`
- `pg_dump`
- `openssh-client`
- `rsync`
- `gzip` 或 `zstd`
- `sha256sum`

### 4.3 推荐技术栈

后端建议使用 Rust：

- 适合构建长期运行的后台服务。
- 类型系统严格，适合沉淀数据库和备份目标适配器。
- 对命令执行、文件处理、并发任务和错误处理有较强控制力。
- 熟悉 Rust 的团队可以获得更好的长期维护性。

Rust 后端建议技术栈：

- Web 框架：`axum`。
- 异步运行时：`tokio`。
- SQLite 访问：`sqlx`。
- 日志与追踪：`tracing`。
- 配置管理：`config` 或 `figment`。
- 定时调度：`tokio-cron-scheduler` 或自研轻量调度循环。
- 加密：`aes-gcm`、`argon2`、`rand`。
- 序列化：`serde`、`serde_json`。
- 命令执行：`tokio::process::Command`。

前端采用 React、Vite、TypeScript 和 pnpm：

- 管理台表单和列表较多，使用成熟前端框架效率较高。
- 第一版可以与后端一起打包为静态资源。
- 本地开发使用 `pnpm dev` 启动 Vite 开发服务器。
- 生产运行和 Docker 镜像使用 `pnpm build` 生成的 `web/dist/` 静态资源，由 Rust 后端直接托管。

元数据库建议使用 SQLite：

- 自部署场景下不需要用户额外安装数据库。
- 足够保存配置、任务、日志和备份记录。

## 5. 核心模块设计

### 5.1 用户认证模块

第一版采用单管理员账号：

- 初始化时通过环境变量设置管理员账号和密码。
- 登录后可以管理全部数据源、备份目标、备份任务和运行记录。
- 后端接口需要鉴权。

后续可扩展为多用户和角色权限：

- 管理员
- 操作员
- 只读用户

### 5.2 数据源管理模块

用于配置需要备份的数据库连接。

核心字段：

- 数据源名称
- 数据库类型
- 主机地址
- 端口
- 用户名
- 密码
- 默认数据库
- SSL 配置
- 数据库类型专属配置

需要提供连接测试能力，用户保存前可以验证配置是否正确。

### 5.3 备份目标管理模块

用于配置备份文件要上传到哪台服务器。

核心字段：

- 目标名称
- SSH 主机地址
- SSH 端口
- SSH 用户名
- 认证方式
- SSH 私钥或密码
- 远端基础目录

需要提供连接测试能力，验证 SSH 是否可连接、目标目录是否可写。

### 5.4 备份任务管理模块

用于配置定时备份任务。

核心字段：

- 任务名称
- 数据源
- 数据库名称
- 备份目标
- 执行周期
- 每日执行时间
- 压缩方式
- 远端保留天数
- 本地临时文件保留天数
- 启用状态

任务需要支持手动立即执行，便于用户验证配置。

### 5.5 运行记录模块

每次备份都应生成一条运行记录。

核心字段：

- 任务 ID
- 开始时间
- 结束时间
- 执行状态
- 失败阶段
- 错误信息
- 原始备份文件名
- 压缩后文件名
- 文件大小
- checksum
- 远端路径
- 执行日志

用户应能在页面上查看最近运行结果和失败原因。

### 5.6 仪表盘模块

首页展示：

- 最近一次备份状态
- 今日待执行任务
- 今日成功任务数
- 今日失败任务数
- 连续失败任务
- 备份文件占用空间概览

## 6. 数据库适配器设计

为了后续方便扩展达梦数据库、SQL Server、Oracle 等数据库，第一版必须把数据库备份能力设计成适配器模式。

业务层不应直接写死 `mysqldump` 或 `pg_dump` 逻辑，而是通过统一接口调用具体数据库适配器。

### 6.1 适配器接口

示例接口：

```rust
#[async_trait::async_trait]
pub trait DatabaseAdapter: Send + Sync {
    fn db_type(&self) -> &'static str;
    fn display_name(&self) -> &'static str;
    fn config_schema(&self) -> DatabaseConfigSchema;
    fn validate_config(&self, config: &DatabaseConfig) -> anyhow::Result<()>;
    async fn test_connection(&self, config: &DatabaseConfig) -> anyhow::Result<()>;
    async fn list_databases(&self, config: &DatabaseConfig) -> anyhow::Result<Vec<String>>;
    fn build_backup_command(&self, job: &BackupJob, output_path: &Path) -> anyhow::Result<BackupCommand>;
    fn build_restore_hint(&self, backup: &BackupRun) -> String;
}
```

### 6.2 适配器职责

每个数据库适配器负责：

- 声明数据库类型。
- 声明该数据库需要哪些配置字段。
- 校验连接配置。
- 测试连接。
- 获取数据库列表。
- 生成备份命令。
- 生成恢复提示。

### 6.3 V1 适配器

第一版实现：

- `mysqlAdapter`
- `postgresAdapter`

MySQL 备份命令建议使用：

```bash
mysqldump --single-transaction --routines --triggers --events
```

PostgreSQL 备份命令建议使用：

```bash
pg_dump -Fc
```

### 6.4 后续扩展达梦数据库

后续支持达梦数据库时，新增 `damengAdapter` 即可。

需要补充：

- 达梦连接配置 schema。
- 达梦连接测试逻辑。
- 达梦数据库列表获取逻辑。
- 达梦备份命令生成逻辑。
- 达梦客户端工具安装或挂载方式。
- 达梦备份文件恢复提示。
- 达梦集成测试用例。

如果达梦客户端工具涉及授权或无法直接打入镜像，则需要支持外挂客户端目录：

- 用户把数据库客户端工具挂载到容器内。
- 系统配置客户端命令路径。
- 适配器使用该路径执行备份命令。

### 6.5 动态配置表单

不同数据库的连接配置不完全一样，前端不应写死一套 `host/port/user/password/database` 表单。

后端适配器应返回配置 schema，前端根据 schema 渲染表单。

例如：

- MySQL 需要 host、port、username、password、database。
- PostgreSQL 可能需要 sslmode、schema。
- 达梦可能需要模式名、字符集、客户端路径或实例参数。

这样后续扩展数据库时，尽量只新增适配器和 schema，不大改前端。

## 7. 备份执行流程

一次备份执行流程如下：

1. 调度器触发任务，或用户点击立即执行。
2. 检查任务是否已在运行，避免同一任务并发执行。
3. 读取数据源、目标服务器和任务配置。
4. 调用对应数据库适配器生成备份命令。
5. 在本地临时目录生成备份文件。
6. 压缩备份文件。
7. 计算 checksum。
8. 生成 manifest 文件。
9. 通过 `rsync` 上传到远端服务器。
10. 验证远端文件存在。
11. 执行远端保留策略，删除过期备份。
12. 清理本地过期临时文件。
13. 写入运行记录和日志。

任一步失败都必须记录失败阶段和错误信息。

## 8. 备份目录规范

远端目录建议采用固定结构：

```text
<base-dir>/<source-server>/<db-type>/<job-name>/<yyyy-mm-dd>/
```

示例：

```text
/data/backups/app-server-01/mysql/order-db-daily/2026-05-14/
```

目录内文件示例：

```text
order-db_2026-05-14_020000.sql.gz
order-db_2026-05-14_020000.sql.gz.sha256
manifest.json
```

## 9. 安全设计

### 9.1 敏感信息加密

以下信息必须加密保存：

- 数据库密码
- SSH 密码
- SSH 私钥
- API token

使用 `APP_SECRET` 作为加密密钥来源。

如果 `APP_SECRET` 丢失，已保存的敏感信息将无法解密，因此安装文档需要提醒用户妥善保存。

### 9.2 最小权限

数据库备份账号应只授予备份所需权限。

备份服务器上的 SSH 用户应只拥有备份目录写入权限，不应使用 root 用户。

### 9.3 命令执行安全

备份命令必须使用参数数组构造，不允许拼接 shell 字符串执行。

用户输入不得直接进入 shell。

## 10. 失败处理与通知

第一版必须记录失败原因，通知能力可以先做基础版本。

建议支持：

- 页面失败状态展示。
- 运行日志查看。
- 连续失败标识。

后续可扩展：

- 邮件通知
- 企业微信通知
- 钉钉通知
- 飞书通知
- Webhook

## 11. 测试计划

### 11.1 单元测试

覆盖：

- 配置加密和解密。
- 数据库适配器注册和查找。
- MySQL 备份命令生成。
- PostgreSQL 备份命令生成。
- cron 解析和下一次执行时间计算。
- 保留策略筛选逻辑。
- checksum 生成。

### 11.2 集成测试

使用 Docker Compose 启动测试环境：

- MySQL 测试实例。
- PostgreSQL 测试实例。
- SSH 备份目标服务器。

验证：

- 数据源连接测试成功。
- 备份目标连接测试成功。
- MySQL 手动备份成功。
- PostgreSQL 手动备份成功。
- 文件成功上传到备份服务器。
- checksum 校验通过。
- 保留策略能删除过期文件。

### 11.3 UI 测试

覆盖关键路径：

- 登录。
- 新增数据源。
- 测试数据源连接。
- 新增备份目标。
- 测试 SSH 连接。
- 新增备份任务。
- 手动执行备份。
- 查看运行记录。
- 查看失败日志。

## 12. 验收标准

第一版完成后，应满足：

- 用户可以通过 Docker Compose 启动系统。
- 用户可以通过浏览器访问管理台。
- 用户可以登录单管理员账号。
- 用户可以配置 MySQL 数据源并测试连接。
- 用户可以配置 PostgreSQL 数据源并测试连接。
- 用户可以配置 SSH 备份目标并测试连接。
- 用户可以创建每日备份任务。
- 用户可以手动执行备份任务。
- 备份文件可以上传到远端服务器。
- 页面可以查看备份成功或失败状态。
- 页面可以查看失败日志。
- 重启容器后配置和历史记录不丢失。

## 14. 关键设计原则

- 第一版优先保证部署简单、备份可靠、失败可排查。
- 数据库能力必须通过适配器扩展，避免硬编码具体数据库。
- 备份目标也应预留适配器能力，方便后续支持对象存储。
- 敏感信息必须加密保存。
- 备份成功不等于可恢复，后续版本必须补充恢复演练和恢复验证能力。
- 所有任务执行都要有可追踪日志，避免用户只看到“失败”但不知道为什么失败。
