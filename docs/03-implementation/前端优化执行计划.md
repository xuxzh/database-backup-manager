# 前端优化执行计划

## 1. 计划目标

本文档用于指导后续 AI 分阶段实施前端优化。计划基于《前端项目评估与优化建议》，将优化项拆成可执行、可验收、可逐步落地的任务包。

执行目标：

- 在不破坏现有功能闭环的前提下，降低前端代码复杂度。
- 让前端结构能承接后续数据库适配器、备份目标适配器和运维体验增强。
- 保持管理台界面冷静、可信、信息密集，不改成营销页风格。
- 每个阶段都能独立验证，避免一次性大改导致回归难定位。

## 2. 执行原则

- 优先小步提交：每个任务包应尽量只处理一个主题。
- 优先保持行为不变：架构整理阶段不新增业务能力，先保证等价迁移。
- 优先复用现有 UI primitives：继续使用 `apps/web/src/components/ui/` 下的 shadcn 风格组件。
- 优先遵守后端 API 契约：API JSON 字段继续使用 camelCase。
- 优先桌面运维体验：移动端保证可用，但不以移动端为主设计目标。
- 不手工编辑 `apps/web/dist/`：前端产物只通过 `cd apps/web && pnpm build` 生成。
- 文档同步：如果实施中改变行为、配置、部署或运维流程，需要同步更新相关文档。

## 3. 当前基线

当前前端入口和关键文件：

- `apps/web/src/App.tsx`：主应用、页面、状态、请求和表单逻辑集中处。
- `apps/web/src/styles.css`：主题 token、布局和业务样式。
- `apps/web/src/api/client.ts`：基础 HTTP 请求封装。
- `apps/web/src/types/api.ts`：前后端 API 类型。
- `apps/web/src/components/ui/`：基础 UI 组件。

当前推荐验证命令：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

如果涉及后端 API 行为或联调：

```bash
cargo run -p backup-manager
```

然后打开 `http://127.0.0.1:8080` 验证受影响流程。

## 4. 总体阶段划分

| 阶段 | 名称 | 主要目标 | 风险级别 |
| --- | --- | --- | --- |
| Phase 1 | 低风险结构整理 | 拆分 `App.tsx`、API 模块、工具函数和通用业务组件 | 低 |
| Phase 2 | 表单模型和校验 | 建立表单模型、转换函数、基础校验和更明确的错误提示 | 中 |
| Phase 3 | Schema 驱动表单 | 接入后端 schema，让数据源和目标表单跟随 adapter 扩展 | 中 |
| Phase 4 | 运维体验增强 | 强化任务执行、运行记录、日志和仪表盘体验 | 中 |
| Phase 5 | 响应式与视觉细化 | 优化表格、移动端、登录页和整体视觉层级 | 低 |
| Phase 6 | 测试体系 | 引入单元测试、组件测试和 smoke test | 中 |

建议严格按阶段推进。Phase 1 完成后再做 Phase 2 和 Phase 3，否则 schema 表单和测试连接能力会继续挤压 `App.tsx`。

## 6. Phase 2：表单模型和基础校验

### 6.1 目标

在进入 schema 驱动前，先建立清晰的表单模型、转换函数和校验规则，减少直接从 `FormData` 拼 payload 的隐性风险。

### 6.2 任务包

#### Task 2.1：建立表单模型和 payload 转换

建议新增：

```text
apps/web/src/features/sources/sourceForm.ts
apps/web/src/features/targets/targetForm.ts
apps/web/src/features/jobs/jobForm.ts
```

执行要求：

- 定义 `SourceFormValue`、`TargetFormValue`、`JobFormValue`。
- 提供 `parseSourceForm`、`parseTargetForm`、`parseJobForm`。
- 提供 `toUpsertDatabaseConnection`、`toUpsertBackupTarget`、`toUpsertBackupJob`。
- 保持最终 API payload 与现状一致。

验收标准：

- 表单提交结果与现有行为一致。
- 表单转换逻辑不再散落在 `App.tsx`。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

#### Task 2.2：增加基础校验和字段级错误

执行要求：

- 端口限制为 1 到 65535。
- 远端保留天数、本地保留天数不能小于 0。
- Cron 表达式至少做基础段数校验，并给出示例。
- 必填字符串 trim 后不能为空。
- 表单错误显示在对应字段附近，顶部保留全局错误。

验收标准：

- 用户输入非法端口时不会发起 API 请求。
- 用户输入非法保留天数时不会发起 API 请求。
- 用户输入明显错误 Cron 时能看到清晰提示。
- 既有后端错误仍能通过 Alert 展示。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

#### Task 2.3：优化禁用状态和空状态

执行要求：

- 没有数据源或备份目标时，新建任务区域显示原因和下一步入口。
- 空列表不只显示“暂无”，还提示建议操作。
- 删除被引用资源失败时，错误信息保留后端原因，并尽量提示先删除相关任务。

验收标准：

- 首次登录空数据状态下，用户能理解下一步应先创建什么。
- 新建任务按钮禁用时，有明确原因。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

## 7. Phase 3：Schema 驱动表单

### 7.1 目标

让前端充分利用后端 adapter schema，使新增数据库类型或备份目标类型时，前端不需要硬编码所有字段。

### 7.2 任务包

#### Task 3.1：加载 schema 数据

修改范围：

- `apps/web/src/types/api.ts`
- `apps/web/src/shared/api/schemas.ts`
- `apps/web/src/App.tsx` 或后续数据容器组件

执行要求：

- 调用 `/api/schemas/databases` 和 `/api/schemas/targets`。
- 将 schemas 纳入页面初始数据。
- 加载失败时展示可理解错误，不影响其他已加载列表。

验收标准：

- 登录后能拿到数据库和目标 schema。
- schema 加载失败时，页面不会白屏。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

#### Task 3.2：实现通用 SchemaForm

建议新增：

```text
apps/web/src/shared/components/SchemaForm.tsx
apps/web/src/shared/schemas/fieldDefaults.ts
```

执行要求：

- 支持 fieldType：text、number、password、select、checkbox。
- 支持 required、default、label。
- 未识别 fieldType 时降级为 text，并保留可见字段。
- 输出结构应能映射到表单模型和 `configJson`。

验收标准：

- MySQL、PostgreSQL、SSH 表单能通过 schema 渲染。
- 默认端口、默认目录等值能正确填入。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

#### Task 3.3：改造数据源和目标表单

执行要求：

- 数据源类型选项来自 database schemas。
- 备份目标类型选项来自 target schemas。
- 类型切换后渲染对应字段。
- 通用字段和扩展字段整理进正确 payload。
- 保留密码、密钥不回显策略。

验收标准：

- 创建 MySQL 数据源成功。
- 创建 PostgreSQL 数据源成功。
- 创建 SSH 备份目标成功。
- 表单字段不再硬编码固定类型列表。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

#### Task 3.4：增加测试连接入口

执行要求：

- 数据源表单增加“测试连接”按钮，调用 `/api/sources/test`。
- 备份目标表单增加“测试连接”按钮，调用 `/api/targets/test`。
- 测试连接不应直接关闭弹窗。
- 测试中展示 loading，成功和失败都有明确提示。

注意：

- 当前后端 `test_source` 和 `test_target` 会创建记录后再测试，这一行为可能不符合“只测试不保存”的直觉。实施前需要确认后端是否要先调整为纯测试接口。
- 如果后端暂不调整，前端文案必须明确“测试会创建临时或实际记录”的真实行为，避免误导用户。

验收标准：

- 测试连接成功时能看到成功提示。
- 测试连接失败时能看到后端错误。
- 保存按钮和测试按钮状态互不干扰。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

涉及真实联调时：

```bash
cargo run -p backup-manager
```

## 8. Phase 4：运维体验增强

### 8.1 目标

将前端从“能配置和执行”提升为“能巡检、能观察、能排障”。

### 8.2 任务包

#### Task 4.1：任务执行进度展示

执行要求：

- 根据 run stage 展示阶段进度。
- 阶段至少包含：等待、准备、导出、压缩、校验、上传、远端验证、清理、完成。
- 失败时停留在失败阶段，并展示错误。
- 保留当前 active run 卡片信息。

验收标准：

- 手动执行后能看到清晰阶段进度。
- 成功、失败、运行中三种状态展示不同视觉反馈。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

#### Task 4.2：日志查看增强

执行要求：

- 日志支持自动滚动到最新。
- 提供复制日志按钮。
- 提供“暂停自动滚动”开关。
- 长日志保持可滚动且不撑破布局。

验收标准：

- 选择运行记录后日志正常加载。
- 新日志追加时能自动滚动。
- 点击复制能复制当前日志文本。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

#### Task 4.3：运行记录筛选

执行要求：

- 支持按任务筛选。
- 支持按状态筛选。
- 支持按关键字搜索错误信息或阶段。
- 筛选先在前端本地完成，除非后端后续提供分页接口。

验收标准：

- 不同筛选条件可组合使用。
- 清空筛选后恢复全部记录。
- 空筛选结果展示明确空状态。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

#### Task 4.4：仪表盘巡检能力

执行要求：

- 最近运行区域展示更多关键字段：任务名、阶段、耗时、远端路径、错误。
- 增加失败聚合或最近失败提示。
- 可从仪表盘跳转到运行记录并定位对应 run。

验收标准：

- 管理员打开仪表盘即可判断最近备份是否健康。
- 从最近失败能进入日志查看。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

## 9. Phase 5：响应式与视觉细化

### 9.1 目标

在保持运维管理台气质的前提下，提升视觉完成度和窄屏可用性。

### 9.2 任务包

#### Task 5.1：表格信息密度和长字段处理

执行要求：

- 对远端路径、错误信息、任务 ID 等长字段增加省略和 tooltip。
- 表头 sticky。
- 操作列保持稳定宽度，减少表格抖动。
- 运行记录错误字段允许展开查看完整内容。

验收标准：

- 长路径和长错误不会破坏表格布局。
- 横向滚动时表格仍可读。

#### Task 5.2：移动端布局优化

执行要求：

- 小屏下侧边栏改为更紧凑的顶部导航或双列导航。
- Dialog 在小屏下接近全屏，底部按钮保持可见。
- 关键表格在小屏下可转为卡片式列表，至少保证字段不重叠。

验收标准：

- 375px 宽度下登录、导航、列表、弹窗可正常使用。
- 页面文字不重叠，按钮文本不溢出。

#### Task 5.3：登录页和整体视觉微调

执行要求：

- 登录页保留管理台气质，可增加部署环境、默认账号提示或安全提醒。
- 仪表盘卡片、运行状态、失败状态的视觉层级更清晰。
- 不引入大面积装饰性背景，不做营销页。

验收标准：

- 视觉比当前更精致，但仍然像运维控制台。
- 颜色不变成单一蓝色或大面积渐变。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

如启动本地服务，应做桌面和移动宽度手动检查。

## 10. Phase 6：测试体系

### 10.1 目标

为后续持续优化提供质量门禁，避免 UI、表单和接口契约回归。

### 10.2 任务包

#### Task 6.1：引入 Vitest

执行要求：

- 增加 Vitest 配置。
- 增加 `pnpm test` 脚本。
- 优先测试纯函数：日期格式化、耗时格式化、stage label、表单转换和校验。

验收标准：

- `cd apps/web && pnpm test` 通过。
- 至少覆盖核心 formatter 和 form parser。

#### Task 6.2：引入 React Testing Library

执行要求：

- 覆盖登录页、空状态、删除确认弹窗、运行日志区域。
- 使用轻量 mock，不依赖真实后端。

验收标准：

- 组件测试能稳定运行。
- 关键交互有断言。

#### Task 6.3：引入 Playwright smoke test

执行要求：

- 增加最小 E2E 流程。
- 使用后端服务或 mock 服务需要提前明确。
- smoke test 场景包括登录、仪表盘、打开创建弹窗、查看空状态或运行记录。

验收标准：

- `pnpm e2e` 或等价脚本能跑通。
- 测试说明写入 README 或 docs。

## 11. 每阶段完成标准

每个阶段完成后，应至少满足：

- `cd apps/web && pnpm typecheck` 通过。
- `cd apps/web && pnpm build` 通过。
- `git status --short` 中只包含本阶段相关文件。
- 关键用户路径没有倒退：登录、刷新、创建资源、删除资源、创建任务、手动执行、查看日志。
- 如果变更影响文档描述，相关文档同步更新。

## 12. 建议提交拆分

建议后续实施时按以下粒度提交：

1. `refactor(web): 拆分前端布局和登录页`
2. `refactor(web): 拆分业务组件和功能面板`
3. `refactor(web): 拆分前端 API 和格式化工具`
4. `feat(web): 增加表单模型和基础校验`
5. `feat(web): 接入 schema 驱动配置表单`
6. `feat(web): 增强备份执行和日志体验`
7. `feat(web): 优化运行记录筛选和仪表盘巡检`
8. `test(web): 增加前端测试体系`

具体提交数量可按实际改动调整，但每次提交应保持主题单一。

## 13. 后续 AI 执行提示词模板
