# Web 前端 UI 与交互优化清单

## 1. 评估范围

本文档聚焦 `apps/web/` 前端管理界面的 UI、交互和前端用户体验，不包含后端执行器、调度器、数据库适配器和部署方案的实现调整。

本次评估基于当前代码静态阅读，主要参考：

- `apps/web/src/App.tsx`
- `apps/web/src/app/AppShell.tsx`
- `apps/web/src/features/auth/LoginPage.tsx`
- `apps/web/src/features/dashboard/DashboardPanel.tsx`
- `apps/web/src/features/sources/SourcesPanel.tsx`
- `apps/web/src/features/targets/TargetsPanel.tsx`
- `apps/web/src/features/jobs/JobsPanel.tsx`
- `apps/web/src/features/runs/RunsPanel.tsx`
- `apps/web/src/shared/components/DataTable.tsx`
- `apps/web/src/styles.css`

当前前端已经完成了第一轮管理台化改造：页面拆分、共享组件、基础表单校验、运行记录筛选、日志复制、日志自动滚动、任务执行状态卡片等能力已经具备。因此下一阶段重点不应是单纯换颜色或增加装饰，而是让备份运维流程更清晰、更可控、更不容易误操作。

## 2. 总体结论

当前界面已经能支撑基础使用，但在真实自部署运维场景中，仍有几类体验短板：

- 创建数据源和备份目标时，前端没有充分利用后端已经提供的 schema 和测试接口。
- 任务创建流程仍偏“填写表单”，缺少计划模板、预览和风险提示。
- 执行过程已有运行卡片和日志，但缺少阶段进度、失败原因聚合和重试入口。
- 表格能承载基础列表，但缺少批量定位、快速筛选、密集信息布局和移动端替代视图。
- 全局刷新和提交状态比较粗，多个操作共享 `isSubmitting`，容易让用户不知道具体哪个动作正在处理。
- 登录页和应用外壳有基础品牌感，但环境、安全和会话状态提示还不够明确。

建议将下一阶段优化目标定义为：

> 把前端从“可操作的管理界面”提升为“面向备份运维人员的高可信工作台”。

## 3. 优先级清单

| 优先级 | 方向 | 主要收益 | 建议阶段 |
| --- | --- | --- | --- |
| P0 | 数据源/目标测试连接 | 降低配置错误，避免任务执行时才暴露问题 | 第一阶段 |
| P0 | 任务创建前置检查 | 避免无数据源、无目标、Cron 错误、保留策略错误导致失败 | 第一阶段 |
| P1 | Schema 驱动配置表单 | 支撑后续更多数据库和备份目标适配器 | 第二阶段 |
| P1 | 执行过程进度化 | 让用户明确当前备份卡在哪个阶段 | 第二阶段 |
| P1 | 失败态诊断面板 | 缩短排障路径，提升运维可信度 | 第二阶段 |
| P2 | 表格筛选和密度优化 | 提升记录增长后的可用性 | 第三阶段 |
| P2 | 响应式和移动端替代视图 | 保证窄屏可用，减少横向滚动 | 第三阶段 |
| P2 | 局部 loading 和操作反馈 | 避免全局提交状态造成误解 | 第三阶段 |
| P3 | 登录页和外壳细化 | 提升产品完整度和环境辨识度 | 第四阶段 |

## 4. 具体优化建议

### 4.1 数据源管理

现状：

- 表单固定支持 MySQL 和 PostgreSQL。
- 端口、名称、主机、用户名、密码已有基础校验。
- `shared/api/sources.ts` 已封装 `testSource`，但 UI 中还没有测试连接入口。
- 数据库类型切换后，端口不会自动随类型变化。

建议：

- 在“新建数据源”弹窗中增加“测试连接”按钮。
- 测试连接成功后，在弹窗内展示成功状态，并允许用户直接保存。
- 测试失败时展示后端错误信息、连接目标、可能原因，例如主机不可达、账号密码错误、数据库权限不足。
- 切换数据库类型时自动带出默认端口：MySQL `3306`，PostgreSQL `5432`。
- 将密码字段旁的说明从“密码会加密保存”扩展为“仅在执行边界解密使用”，增强安全可信度。
- 数据源列表增加“最近测试时间”或“连接状态”占位，后续如果后端支持健康检查可直接接入。

验收标准：

- 用户不用创建任务，就能确认数据源连接是否可用。
- 类型切换不会留下不合理默认端口。
- 连接失败能给出明确错误，而不是只出现全局错误条。

### 4.2 备份目标管理

现状：

- 表单固定为 SSH 目标。
- `authMethod` 支持 key/password，但“密钥或密码”共用一个 password input。
- `shared/api/targets.ts` 已封装 `testTarget`，但 UI 中还没有测试目标入口。
- SSH 私钥通常是多行文本，当前单行输入不利于粘贴和检查。

建议：

- 在“新建备份目标”弹窗中增加“测试目标”按钮。
- 认证方式为 `key` 时，将密钥输入改为多行 textarea；认证方式为 `password` 时使用 password input。
- 根据认证方式动态调整字段文案：`SSH 私钥` 或 `登录密码`。
- 增加远端目录有效性提示，例如目录不存在时由后端测试返回明确错误。
- 目标列表中对远端目录做省略展示，并提供 tooltip 或点击复制。
- 后续增加本地目录、S3、对象存储等目标时，应由 schema 驱动字段，而不是继续复制固定表单。

验收标准：

- 用户可以在保存前确认目标主机、认证方式和远端目录可用。
- SSH 私钥可以自然粘贴，不被单行输入框破坏可读性。
- 列表中长路径不挤压操作列。

### 4.3 备份任务管理

现状：

- 无数据源或无目标时，新建按钮会禁用并通过 tooltip 说明原因。
- Cron 只做 5 到 6 段的基础格式校验。
- 任务列表展示名称、数据源、数据库、目标、计划、启用状态和操作。
- 手动执行后有执行中状态卡片，但任务列表缺少最近一次结果和下一次执行语义。

建议：

- 新建任务弹窗增加 Cron 常用模板：每天 02:00、每 6 小时、每周日 03:00。
- Cron 输入旁增加“下次预计执行时间”预览；如果暂时不接 cron parser，也应先提供模板减少手输。
- 任务列表增加最近一次结果、最近运行时间、最近耗时。
- 对正在执行的任务，在列表行内展示运行中状态，并禁用重复触发。
- 对未启用任务，使用更弱的视觉状态，同时提供“启用/停用”快捷操作。
- 创建任务时，如果数据源或目标为空，除禁用按钮外增加空状态引导按钮，跳转到对应 tab。
- 删除任务前提示是否已有运行记录，以及删除后是否保留历史记录，避免用户误解。

验收标准：

- 用户创建定时任务时不需要熟记 Cron 语法。
- 运维人员扫一眼任务列表即可知道哪些任务健康、哪些任务最近失败。
- 重复触发和误删风险下降。

### 4.4 运行记录与日志

现状：

- 运行记录支持按任务、状态、错误/阶段搜索。
- 日志支持自动滚动、暂停滚动和复制。
- 运行记录表格展示错误信息，但失败原因仍分散在表格和日志中。

建议：

- 增加失败详情面板：状态、失败阶段、错误信息、最近几条日志、可能操作。
- 日志行按 `level` 增加轻量颜色区分，例如 error/warn/info。
- 日志区增加“只看错误”“只看当前阶段”筛选。
- 选中运行记录后，在日志区标题处展示任务名称、开始时间、耗时和阶段。
- 支持从最近运行、任务列表和运行记录之间稳定跳转，并保持选中态。
- 运行记录增加时间范围筛选：今天、最近 7 天、最近 30 天。

验收标准：

- 失败后用户能在一个区域看到“在哪失败、为什么失败、下一步看什么”。
- 日志很多时仍能快速定位错误行。
- 从仪表盘进入某次运行详情后，上下文不会丢失。

### 4.5 仪表盘

现状：

- 已展示数据源、备份目标、任务、启用任务、今日成功、今日失败。
- 已展示最近运行和今日失败提醒。

建议：

- 增加“需要关注”区域：今日失败任务、连续失败任务、长时间未运行任务。
- 增加最近 24 小时成功/失败概览，优先使用紧凑列表或小型趋势，不做大面积装饰图。
- 统计卡支持点击跳转，例如点击“今日失败”进入已筛选的运行记录。
- 最近运行卡片中补充任务名称，而不仅是运行阶段。
- 如果没有任何数据源/目标/任务，仪表盘展示配置引导路径：数据源 -> 备份目标 -> 任务 -> 手动执行。

验收标准：

- 仪表盘能回答“现在有没有问题”和“下一步该去哪处理”。
- 空系统第一次打开时，用户知道配置顺序。

### 4.6 全局外壳与导航

现状：

- 侧边栏、顶部标题、刷新、退出登录已经清晰。
- 通知和错误使用全局 Alert。
- 小屏幕下侧边栏会变成静态块，导航为两列。

建议：

- 顶部区域增加当前刷新时间，例如“最后刷新 14:32:10”。
- 全局刷新按钮只表现刷新行为，提交保存、测试连接、执行任务使用各自的局部 loading。
- 全局 Alert 增加关闭按钮，避免成功消息长期占位。
- 窄屏下侧边栏改为更紧凑的顶部导航或可折叠菜单，减少首屏被导航占满。
- 退出登录前如果正在提交或执行测试，给出确认或禁用。

验收标准：

- 用户能区分“页面在刷新”“某个表单在保存”“某个任务在执行”。
- 小屏幕下首屏仍以业务内容为主，而不是被导航挤压。

### 4.7 表格与信息密度

现状：

- `DataTable` 已有 sticky header、横向滚动、空状态和长字段省略。
- 所有表格仍以统一列渲染为主，移动端主要依靠横向滚动。

建议：

- 为 `DataTable` 增加列级配置：宽度、对齐、省略、是否可复制、移动端展示标签。
- 对 ID、路径、错误等长文本统一提供 tooltip 和复制按钮。
- 移动端将关键表格切换为资源卡片，而不是继续横向滚动。
- 增加表格密度选项或默认更紧凑的行高，适配运维扫描。
- 空状态不只显示文本，还应带主操作按钮，例如“新建数据源”。

验收标准：

- 长字段不会破坏布局。
- 运维人员能快速扫描列表，不需要频繁横向滚动。
- 空状态直接告诉用户下一步操作。

### 4.8 表单与校验

现状：

- 已有 `validators.ts`，覆盖端口、保留天数、必填和 Cron 基础格式。
- 各 feature 内部仍维护独立 `fieldErrors`。
- 提交失败主要通过全局错误展示。

建议：

- 抽象统一的表单错误展示模式，减少每个面板重复维护 `fieldErrors`。
- 对数字输入增加 `min`、`max`、`step`，让浏览器原生约束和前端校验一致。
- Cron 使用模板和预览降低输入错误，而不是只在提交时提示错误。
- 表单提交失败时，将后端字段级错误映射到具体字段；没有字段信息时再展示全局错误。
- 保存成功后不要简单 `form.reset()`，应根据场景关闭弹窗或保留用户刚创建的摘要。

验收标准：

- 错误提示出现在具体字段旁边。
- 后端错误不会只在页面顶部一闪而过。
- 表单控件原生约束和前端校验规则一致。

## 5. 建议实施阶段

### 阶段一：高价值低风险交互

目标：优先解决保存前不可验证、Cron 难填写、局部反馈不清的问题。

任务：

- 数据源弹窗接入 `testSource`。
- 备份目标弹窗接入 `testTarget`。
- 数据库类型切换自动更新默认端口。
- 备份目标认证方式动态切换输入控件。
- 任务表单增加 Cron 模板。
- 新建任务空状态增加跳转引导。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

如涉及真实接口联调，再启动后端并手动验证：

```bash
cargo run -p backup-manager
```

### 阶段二：执行可观测性

目标：让用户更容易判断任务是否正常、失败后怎么排障。

任务：

- 运行详情区域增加失败诊断面板。
- 日志按 level 做视觉区分。
- 日志增加错误过滤。
- 任务列表增加最近运行结果。
- 仪表盘统计卡支持跳转到筛选后的运行记录。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

建议准备成功、失败、运行中三类运行记录进行手动验证。

### 阶段三：Schema 驱动与扩展性

目标：让前端可以承接更多数据库和备份目标类型。

任务：

- 前端加载 `/api/schemas/databases` 和 `/api/schemas/targets`。
- 新增通用 `ConfigSchemaForm` 组件。
- 数据源和目标表单改为“基础字段 + schema 扩展字段”。
- `configJson` 由 schema 表单统一生成。
- 补充 schema 表单单元测试。

验证：

```bash
cd apps/web
pnpm test
pnpm typecheck
pnpm build
```

### 阶段四：表格和响应式体验

目标：提升记录增长和窄屏使用时的可用性。

任务：

- `DataTable` 支持列级配置。
- 长文本 tooltip 和复制按钮统一封装。
- 移动端资源卡片视图。
- 全局外壳增加最后刷新时间。
- Alert 支持手动关闭。

验证：

```bash
cd apps/web
pnpm typecheck
pnpm build
```

如有条件，使用桌面和窄屏视口分别打开 `http://127.0.0.1:8080` 检查布局。

## 6. 不建议优先做的事项

- 不建议先做大面积视觉重绘。当前视觉基础可用，真正影响体验的是运维流程和反馈。
- 不建议把管理台改成营销页风格。该系统面向自部署运维，应该保持克制、清晰、信息密集。
- 不建议在 schema 表单之前继续为每种新数据库复制一套固定字段。
- 不建议立即引入大型状态管理库。当前规模下可先通过 feature API 和局部状态整理解决问题。
- 不建议手工编辑 `apps/web/dist/`。生产产物应继续通过 `pnpm build` 生成。

## 7. 推荐下一步

建议优先实施“阶段一：高价值低风险交互”。这组改动对用户感知最明显，同时不会改变后端数据模型：

1. 接入数据源测试连接。
2. 接入备份目标测试。
3. 优化 SSH key/password 动态表单。
4. 增加 Cron 模板。
5. 增加局部 loading 和测试结果提示。

完成后再推进执行可观测性和 schema 驱动表单，会更稳。
